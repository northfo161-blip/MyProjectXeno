## Gate relationship: G4 versus G2

The two gates are separate and must not be conflated.

- **G4 (task authorization).** The owner approves *this task spec*. Approval means the spec is
  complete enough to execute: the intended tool, exact version, pin file, commands, artifact
  path, verification procedures, allowed files, and acceptance criteria are all fixed and
  reviewable. G4 approval of this spec is what makes the work permitted.
- **G2 (tooling).** The owner installs the tool or explicitly authorizes its installation.
  G2 is required by `AGENTS.md` §11 before any install, and it is a **separate** decision from
  G4. Approving this spec at G4 does **not** authorize installing Rojo, Rokit, or the Studio
  plugin.

Required order: this spec completed → **G4** → **G2** install/authorization → M0 tests. In
addition, `AGENTS.md` §11 G2 requires that the specific tool, version, and pin file be named in
the **approved** task spec before installation; that is this document's job, and it is not yet
done.

Establish a reproducible, reviewable path from repository files into Roblox Studio: a pinned
toolchain, a project mapping file, and a three-folder skeleton that can be built into an
openable place and live-synced into Studio, with no gameplay code.

## Gameplay and technical requirements

1. **No gameplay.** Only the three placeholder files exist; each prints or exposes a marker
   and nothing else. No `RemoteEvent`, no service module, no loop.
2. **Mapping.** The mapping file maps exactly the three disk folders to the three containers
   named in `ROADMAP.md` §4 M0, and the containers are `Folder` instances; entry-point scripts
   live *inside* them.
3. **No folder-to-script promotion at the roots.** No `init.server.luau` / `init.client.luau`
   at `src/server` or `src/client`, because that would turn the container into a `Script`
   (`ARCHITECTURE.md` §3.2).
4. **Naming.** PascalCase modules; `*.server.luau` and `*.client.luau` entry points
   (`AGENTS.md` §6.4).
5. **Pinned versions.** The pin file records the exact Rojo version and the installed version
   is compared against it (T-M0-06).
6. **Portable paths.** No absolute path, drive letter, or user name appears in any committed
   file (`AGENTS.md` §1.1; T-M0-05).
7. **Separate build and sync.** The artifact build and the live-sync mechanism are configured
   and verified independently; passing one does not substitute for the other.
8. **Artifact placement only.** Build output goes to `build/`. This is a directory choice, not
   an asset policy: it does not decide whether generated files are ignored or committed, and
   it does not unblock T-M0-08.
9. **Visible failure.** Losing the sync connection is observable; stale Studio content is never
   silently presented as current (T-M0-07).
10. **No scaffolding.** No Command Bar snippet, temporary script, or repository-side test
    harness is created, because Q-06/A-12 is undecided.

## Beginner setup steps (provisional — to be verified at G2)

These steps are written for the provisional Rojo + Rokit direction. They are **not** authorised
yet, and the owner confirms them as repeatable only after performing them at G2.

1. **Confirm the version.** The pinned Rojo version is `7.7.1`; do not substitute a "latest"
   download.
2. **Install Rokit** (owner action at G2, if this route is authorized): run the Windows installer
   or `rokit.exe` / `rokit.exe self-install` as documented by Rokit.
3. **Install the pinned tool:** from the repository root, `rokit install`. Record its output.
4. **Install the Studio plugin** by the one authorised method only; record how it was installed
   and its version.
5. **Verify versions:** compare `rojo` output and the plugin version against `rokit.toml` and
   paste the output.
6. **Build:** `rojo build -o build/<artifact>` from the repository root; confirm the artifact
   appears under `build/`.
7. **Open** the artifact in Studio; confirm the three containers are `Folder`s containing the
   placeholder scripts.
8. **Sync:** `rojo serve`, then connect from the plugin panel; confirm a live connection is
   shown.
9. **Round-trip test:** change the marker on disk, watch Studio update, revert, watch again.
10. **Disconnect test:** stop `rojo serve` and confirm the disconnected state is visible.
11. **Recovery:** if the port is in use, a file is locked, or the connection fails, record the
    exact message rather than guessing a workaround. (Rojo 7.7.0 documents clear errors for a
    port in use, read-only or locked files, and filesystem-watcher failures.)

## Risks and notes

- **R-01 (unverified):** sync reliability with the installed Studio build on Windows. This draft
  makes **no** compatibility claim for Rojo 7.7.1 or its plugin against Studio 0.744.0.7441077;
  test steps 4–6 settle it, and a failure is reported rather than worked around.
- **Windows path handling:** Rojo 7.7.1 fixed a fault where `rojo serve` *silently stopped
  syncing* on Windows when the served path was a verbatim (`\\?\`) path, and fixed `$path` and
  sourcemap failures for paths outside the project folder. Pinning an older version would
  reintroduce a silent-failure risk that T-M0-07 exists to catch.
- **Line endings:** this machine has `core.autocrlf=true` and the repository has no
  `.gitattributes`. Rojo documents converting synced Lua files to LF; that behaviour must still
  be recorded during verification rather than assumed.
- **Folder promotion:** an `init.*.luau` file at a root folder would turn a container into a
  script and fail T-M0-02 (`ARCHITECTURE.md` §3.2). Rojo documents this behaviour explicitly.
- **Rokit is itself a tool.** Its own version is not pinned by `rokit.toml`, so “pinned” applies
  to Rojo, not to the manager. Record the Rokit version used.
- **Publishing capability:** `rojo upload` can publish a place when given credentials. Uploading
  is Gate G7 and is forbidden in M0; no cookie or account credential may be configured.
- **Plugin install is a tool install.** Choosing the plugin route is part of G2, not a
  consequence of this spec.
- **D-16 boundary (explicit).** Naming `build/` as the artifact directory does **not** decide
  whether generated place files are ignored or committed, does **not** authorize committing a
  place file, and does **not** unblock T-M0-08. T-M0-08 stays `BLOCKED` until the owner records
  D-16.
- **Q-06/A-12 boundary (explicit).** No Command Bar snippet, temporary script, or repository
  test scaffolding is created or permitted; the checks above are manual observations only.
- **Q-09 boundary (explicit).** The L4 `NOT APPLICABLE` rule for M0 is still derived, still
  pending, and must be labelled as such in any acceptance record.
